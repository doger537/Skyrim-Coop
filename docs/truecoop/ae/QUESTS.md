# Сверка квестов при входе в кампанию

`QuestSyncPolicy` задаёт правила для первичного импорта, сверки персонажа, сетевых событий и восстановления журнала SQLite. Для новых кампаний хост передаёт историю квестов один раз. После подтверждения сервер публикует одну ревизию журнала для обоих игроков.

| Категория | Правило |
| --- | --- |
| Сюжет | Значимые стадии, завершение и зафиксированные решения должны совпасть. Сверка допускает только проверенные различия истории Хелгена при общих контрольных стадиях. |
| Локальное | Проверенные контроллеры сцен и эффекты персонажа остаются в конкретном сохранении. Например, контроллер атаки дракона в Хелгене и сцена с рычагом Bleak Falls Barrow. |
| Радиантное | У проверенных заданий Соратников стадии 0 и 1 означают подготовку предложения. Со стадии 10 начинается игровой прогресс. При входе сверяются значимые стадии и состояние выполнения. |
| Общее | Совпадают локальные и серверные стадии. Повтор допустим только для записанного события из закреплённого списка безопасных стадий. У `None` и `Miscellaneous` сохраняются настройки сервера и адаптеров. |

Если сверка находит конфликт, в `Data/SkyrimTogetherReborn/logs/tp_client.log` появляется запись `Campaign quest admission` для каждого несовместимого квеста. Запись включает серверный ID и ID формы в игре, EditorID, тип, причину, стадии и состояние с обеих сторон. Skyrim не предоставляет сетевой `Epoch` локального сохранения. В журнале этот показатель обозначен как `unknown`, а локальный `Started` отмечен как вычисленный по наблюдаемому состоянию. Сверка проверяет весь набор до применения любого запланированного повтора.

Старые строки SQLite с локальными сценами и импортированными предложениями сохраняются. Сервер исключает их из публикуемого журнала и учитывает их ревизию. При первом принятии радиантного задания сервер заменяет прежнюю строку атомарно с проверкой её ревизии. Изменение схемы базы для этого не требуется. История с живыми событиями старой сборки сохраняется под строгой проверкой.

## Хелген и дорога в Ривервуд

Проверены записи `QUST` и таблицы `VMAD` базового `Skyrim.esm`, а также операции соответствующих скомпилированных фрагментов из `Skyrim - Misc.bsa` установки 1.7.104.0. У `MQ101` стадии 8 и 9 устанавливают разные значения `FactionPath`. Стадия 250 выбирает соответствующего спутника и союзников. Стадия 700 вызывает уборку Алдуина на выбранном маршруте. Стадия 800 передаёт управление `MQ102A` или `MQ102B`. Стадии 900 и 1000 отмечают выход и завершение пролога.

После общего завершения допускаются проверенные различия в истории подсказок, пещеры и уже завершившихся сцен. Список для `MQ101`: 258, 280, 315, 317, 318, 320, 340, 368, 380, 395, 470, 550, 560, 630, 700, 720, 725, 730, 750. Стадии 8, 9 и все остальные стадии проходят точную сверку. У обоих персонажей должны совпадать значимые стадии каждого маршрута и основного `MQ102`.

Для `MQ102B` (0002610A) стадия 3 выключает Алдуина из пролога, а стадия 10 задаёт другую сторону игрока, Ралофа и Гердур. Значимые стадии `MQ102B` сверяются самостоятельно. Вызов фрагмента уборки при подключении не выполняется. Стадии с пустыми фрагментами также остаются в сравнении, поскольку их могут читать условия игры.

## Предложения Соратников

У `CR01`, `CR02`, `CR04`–`CR08` фрагмент стадии 0 вызывает `CompanionsRadiantQuest.Setup`. Он регистрирует подготовленное предложение в `CR00` и устанавливает стадию 1. У `CR04` первой видимой целью управляет `Fragment_5` стадии 10. Другие проверенные цепочки используют тот же порог. Показывать или принимать предложение может каждый персонаж в своей игре. Стадии после принятия учитываются в общем журнале. Подключение не запускает и не продвигает эти квесты через Papyrus.

Правила рассчитаны на проверенные записи и скрипты Bethesda. Изменения этих записей сторонними модами требуют отдельной проверки. У принятого радиантного задания сверка покрывает стадии и жизненный цикл. Совпадение случайно выбранной цели по ссылке движка и выдача наград требуют отдельного игрового прогона.

## Проверки

- `TPTests "[quest.admission],[quest.replay],[quest.migration]"` проверяет безопасные различия, отказ по несовместимым веткам, импорт и запись принятого задания после восстановления базы.
- `Tools/TrueCoop/Test-QuestAdmission.ps1` запускает отдельный сервер и двух клиентов протокола с разными наблюдениями после Хелгена. Проверяются первое подключение, повторный вход того же персонажа и сохранение ревизии журнала после перезапуска.
- Для проверки в Skyrim нужны два экземпляра игры 1.7.104.0. Каждый загружает отдельное сохранение после выхода из Хелгена по одному маршруту. Далее оба подключаются, отключаются и повторяют вход после перезапуска сервера.

## Предыдущий этап разработки

Главное правило остаётся целью: один сюжет и один результат решений для сервера.
Индивидуальные сюжетные ветки и отдельные версии мира не добавляются.

Исправлен конкретный дефект прежней ретрансляции: повторный Started от второго
участника стирал множество уже переданных стадий. Следующий повтор StageUpdate
снова отправлялся группе. `QuestEventHistory` подавляет повтор Started/Stopped,
сохраняет стадии до явного Stopped → Started и разрешает повторяемые задания.
Поздний первый Started также не стирает ранее полученные стадии.
Число стадии не используется для выбора «правильной» сюжетной ветки.

**Реализовано, игровая проверка не выполнена.** Это исправление в существующем
party relay, не готовая общая кампания. История пока живёт в группе в памяти.
Общесерверный постоянный журнал, конфликтующие решения, поколения перезапуска
квестов и безопасный поздний вход не реализованы. Поздний Started после Stopped
без идентификатора запуска всё ещё нельзя отличить от настоящего рестарта.
Misc/None-квесты остаются под прежней экспериментальной настройкой; включать её
для всей AE-поставки без испытаний нельзя.

## Матрица адаптеров

Приоритетные прогоны: Fishing, Saints & Seducers, The Cause, Ghosts of the Tribunal,
Forgotten Seasons, Bittercup, Farming, Bloodchill Manor, Survival Mode, Nchuanthumz.
Остальные 64 записи также требуют анализа QUST/VMAD: имя плагина и наличие оружия
не доказывают отсутствие квестового скрипта. Ни один адаптер пока не объявлен готовым.

Для каждого фактического QUST заполнить:

| Поле | Обязательные сведения |
|---|---|
| Identity | plugin SHA-256 + local QUST FormID, версия ресурсов |
| Prerequisites | masters, начальные стадии, aliases и зависимые globals |
| Events | стадии, Stop/Start, диалоги, сцены, Papyrus fragments, rewards |
| Decisions | взаимоисключающие варианты и одно авторитетное решение |
| Replay | какие операции идемпотентны, какие нельзя повторять при входе |
| Recovery | журнал/поколение/сверка сейва, обрыв до и после фиксации |
| Evidence | два клиента, действия обоих игроков, поздний вход, награды, перезапуск |

Для решений понадобится серверная последовательность операций и сохранённый
результат до рассылки. Для Papyrus требуется анализ реальных скриптов и поведения
движка. Новые хуки и offset-ы без IDA/Ghidra здесь не угадывались.

Alternate Start policy, исключение личных начальных форм и scene guards сохранены.
MAST теперь проверяется для всех активных плагинов, включая актуальные зависимости
USSEP. Конкретный набор ASLAL+USSEP+AE ещё должен пройти AE-START из игрового плана.
