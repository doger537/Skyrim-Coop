# План стабилизации совместного прохождения AE

Базовая ревизия — `e96dcdbf`, исходный код защиты стадий сцен восстановлен в `addab9e4`. Игровой runtime для прогона — SkyrimSE.exe **1.7.104.0**. Прохождение сценария двумя клиентами Skyrim фиксируется отдельно от компиляции и сетевых проверок без игры.

## Исходное состояние

| Подсистема | Реализовано | Открытая проверка |
| --- | --- | --- |
| Квесты | `QuestSyncPolicy` классифицирует локальные, сюжетные и общие квесты. Сервер ведёт журнал с эпохой запуска и ревизией. Клиент проверяет допуск и подтверждает входящие стадии по состоянию Skyrim. | Журнал охватывает стадии и решения. Значимые цели, состояние VM и зависимости между квестами требуют отдельной проверки. |
| Сцены | `addab9e4` восстановил ожидание сцен на стороне получателя. Сохраняется порядок стадий одного квеста, ожидание не расходует время проверки вызова движка. | Условия завершения могут состоять из нескольких связанных проверок. Нужен игровой прогон для реальных сцен и асинхронных фрагментов. |
| Papyrus и награды | `QuestGrantService` и `SharedQuestEffectService` доставляют проверенные эффекты `AddItem` и `RemoveItem` для базовых форм из поддерживаемых квестовых фрагментов. Операции используют серверные квитанции и отдельные курсоры применения. | Скрипты диалогов, сцен и произвольные эффекты требуют анализа и отдельных адаптеров. |
| Диалоги, NPC, предметы | `DialogueService` передаёт намерение разговаривать владельцу NPC. Есть эпохи владения, воспроизведение движения и поз, поддерживаемый рагдолл и записываемые сервером обычные предметы. | Смена владельца при уходе из ячейки, сложные анимации и общие физические позы требуют игрового прогона. |
| Контрольная точка | `WorldCheckpointService` согласует манифест двух файловых наборов, состояние SQLite, канонический физический кадр и новую эпоху при загрузке. | Прерывание выдачи или сцены и восстановление VM после двух реальных загрузок. |

## Порядок изменений

1. **Стадии и сцены.** Учитывать группы условий AND/OR и весь необходимый префикс стадий. Использовать существующие `GetStage`, `GetStageDone` и события сцены. Подтверждение результата Skyrim и порядок стадий сохраняются.
2. **Ранний контроль гостевых действий и эффекты.** Установить точку, где выбор гостя можно проверить до необратимого скрипта. Подключать только доказанные операции через имеющиеся квитанции. Для каждой операции проверить повторную доставку и прерывание между разрешением, применением и записью результата.
3. **Сюжетное состояние.** Сначала читать и сравнивать проверенные алиасы, globals и состояния конкретных NPC. Запись допускается при наличии проверенного API для конкретной операции. Исследовать зависимости сцен между квестами и привязать их к проверенным формам.
4. **Сверка и восстановление во время сессии.** Сравнивать наблюдения игроков по подтверждённой ревизии и эпохе мира. Отличать отложенное применение от подтверждённого конфликта. Предлагать восстановление через существующую парную контрольную точку.
5. **Владение, движение и физика.** Использовать существующие очереди и интерполяцию. Проверять нагрузку, единственные источники обновлений, смену владельца и ячейки. Повторить прогоны при задержках, дублях пакетов и разрывах связи.

## Этап 1. Сценарии для двух Skyrim

Оба игрока устанавливают сборку одной ревизии. Для контроля используйте отдельный тестовый мир и одинаковый активный контент. Сохраните первую согласованную точку через `/coop-save`. Перед копированием остановите сервер. Для восстановления понадобятся ZIP, каталог SQLite с сопутствующими файлами и оба набора `.ess`, `.skse` при наличии и `.tcphys`.

| Сценарий | Действие | Что считать успешным |
| --- | --- | --- |
| Реплика на стороне гостя ещё идёт | Лидер продвигает общую стадию в сцене, которая проверяет эту стадию. Гость продолжает слушать. | Реплика заканчивается. После этого сцена и стадии двигаются в порядке. Ожидание реплики дольше пяти секунд не приводит к отказу подтверждения. |
| Фаза ждёт несколько стадий | На тестовом квесте фаза зависит от двух `GetStageDone`. Между стадиями есть пауза. | Ранний выпуск возможен, когда очередь содержит достаточную последовательность, реплики закончились и всё условие становится истинным. Срабатывание одной части AND не разрешает ранний выпуск. |
| Условие с неизвестной проверкой | Фаза использует условие стадии совместно с отдельным глобальным или внешним условием. | Клиент даёт сцене продвигаться по правилам Skyrim. Достаточность неизвестного условия не угадывается. После естественного завершения блокирующей фазы очередь продолжает работу. |
| Повтор и переподключение | После квестовой стадии переподключить гостя, сверить журналы и поведение сцены. | Полученная ранее стадия не вызывает повтор фрагмента. При неподходящем сейве виден точный квестовый отказ. |
| Общая загрузка | После сцены выполнить `/coop-load N` для сохранённой точки. | Оба получают свои файлы. Ни одна старая очередь стадий не применяется после смены эпохи. |

Для каждой попытки записать ревизию сборки, EditorID квеста, стадию, действия обоих игроков и строки `Quest scene stage` или `Quest application failed` из `tp_client.log`. Результаты компиляции, синтетического протокола и двух окон Skyrim отмечаются отдельно.
