# Host approval of guest quest changes

This describes source implementation, not a completed gameplay test. On 2026-11-18 the user explicitly deferred automatic and gameplay tests. Compilation is the only executable validation for these new changes so far.

In a two-player party the server queues guest Started/StageUpdate/Stopped changes instead of committing them immediately. The current party leader is the host for this approval. Before sending a proposal, `Campaign::State::PreviewQuest` performs the exact same content, run, type, stage and story-decision validation as commit, without writing any state or participant ownership. Already accepted changes receive the normal idempotent acknowledgement.

The host receives a bounded, checked message. A copied proposal crosses the existing runner queue; no engine pointer crosses threads. On a later runner frame the client reuses the existing live quest application with its echo override and scene guards. It reports acceptance only after observing the native started/reached/stopped condition. This is a stage/lifecycle acceptance signal, not proof that every latent Papyrus fragment has finished or that item effects have been delivered.

The server accepts the decision only from the pinned host/player identity in the same party and WorldEpoch. It revalidates on commit. The original guest remains the durable initiator of the new quest run. Host-generated stage events for that pending run are held behind the initiating event, so they cannot accidentally replace its owner. Successful commit broadcasts the authoritative journal revision; the initiator receives an acknowledgement without replaying its already local fragment. A host echo of an already stopped quest no longer stops it twice.

The server queue is bounded to 64 proposals and one in-flight approval. The host queue is bounded to 16 copied messages. Waiting uses ticks, not a render-thread network wait. An in-flight proposal expires after 180 seconds (host rejects locally after 170 seconds). Party/host changes, disconnects and world-epoch changes invalidate proposals. If the native host application may already have happened when approval fails, both participants must return to a matching checkpoint; the code refuses to conceal a divergent host state. Common save/load cannot start while approvals remain pending. Single-player sessions retain the existing direct journal path; imported quest histories do not invent an initiator.

Protocol `0x5443000A` adds proposal/decision messages and checked fixed-width quest update layouts. Quest packets validate every field before applying native state; partial reads no longer use an uninitialized temporary. GameId defaults now initialize both words to zero. Branch/library build identity remains mandatory in addition to protocol version.

Remaining limits: this is not an engine-wide rollback of the guest's local VM effects before approval, and it does not implement exactly-once native quest item/reward delivery. That requires the separate verified latent-functor gate and saved inventory receipt path described in `QUEST_GRANTS.md`. A pinned replay adapter is still required for unsupported historic quest replay. No change was made to Alternate Start.
