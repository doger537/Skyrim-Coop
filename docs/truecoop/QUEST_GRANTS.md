# Журнал квестовых выдач и источник Papyrus

Статус: backend и движковое наблюдение реализованы; **автоматическая выдача в инвентари ещё не подключена**. Классификацию предмета и фактическую выдачу нельзя считать подтверждёнными одним вызовом AddItem или сетевым ACK.

Обновление 18.11.2026: пользователь отложил все тесты. Диагностический квест/запускатель оставлены для будущей проверки, игру не запускаем. Новые изменения допуска по файлам и подтверждения квестов хостом проходят только проверку исходников/компиляцию; старые 112 тестов к ним не относятся. Текущие границы — `IMPLEMENTATION_20261118.md`.

## Готовый серверный слой

`QuestGrantPlan` описывает заранее классифицированное событие: квест, эпоху запуска, принятую стадию, постоянного инициатора и устойчивый ID события адаптера. В одном плане до 32 предметных эффектов. У предмета роль `Key` или `Reward`; флаг quest item должен ей соответствовать. Планы с неположительными/чрезмерными количествами, неверными формами или нечисловыми эффектами не фиксируются.

`CommitQuestGrant` создаёт один неизменяемый receipt и **оба** индекса доставки в одной SQLite-транзакции. Повтор того же плана возвращает исходную ревизию; замена количества/предметов под тем же ID отклоняется. Инициатор проверяется по `quest-run`, стадия — по принятому неимпортированному событию журнала. Для старой импортированной истории владелец не выдумывается.

Проекция receipt для инициатора включает ключевые предметы и награды; для второго участника — награды. Оба получают одинаковые свойства уникального предмета, включая динамические зачарования. Флаги экипировки снимаются: передача награды сама не должна экипировать её у второго игрока. Это модель доставки, а не выполненный AddItem.

Записи `quest-grant/` и `quest-inbox/` возвращаются парным checkpoint вместе с журналом и инициаторами. При открытии/откате мира проверяется наличие обоих индексов и их соответствие receipt/участникам; сиротские индексы и потерянный получатель останавливают открытие. Очередь читается страницами до 64 записей. Ревизионная страница не разрезает одну транзакцию молча. ACK не удаляет receipt: для этого слоя ещё нет сохранённой клиентской квитанции.

Новые базы используют SQLite schema **3**. Schema 1/2 мигрирует с сохранением UUID мира, ревизии и записей; старые серверы, не знающие журнал выдач, отказываются открывать schema 3. Не подставляйте новую серверную базу старой сборке и не понижайте `user_version` вручную.

**Публичного сетевого обработчика, принимающего произвольную классификацию от клиента, нет.** Следующий игровой сервис должен принимать роли/ID события из проверенной политики квеста. Иначе временный инструмент, возврат денег или обычный скриптовый подарок будут ошибочно названы наградой. Существующий реестр игровых адаптеров остаётся пустым; `game_verified` не выставлялся по результатам unit-тестов.

## Готовое движковое наблюдение

`NativeQuestContext` охватывает **выполнение** отложенного AddItemFunctor, не SetStage. Он берёт временную retained-ссылку на VM stack, копирует self-variable, находит ближайший связанный Quest/Alias/TopicInfo/Scene, копирует имена скрипта/функции и offset инструкции. Retained stack корректно освобождается также при последней ссылке. Engine pointers не покидают вызов; в `InventoryChangeEvent` попадает только копия контекста. Отдельно учтены actor AddInventoryItem и pickup-reference: одного хука TESObjectREFR недостаточно.

Наблюдение включается после допуска кампании на runner-потоке, отключается при disconnect. На другом потоке и офлайн оригинальный вызов проходит без чтения VM. Обход ограничен 64 кадрами, имена — 128 байтами. Оригинальный AddItem, его результат и расписание VM сохраняются. Эта версия не подавляет предметы и не добавляет награды.

В debug-журнале `Quest item source` указывается связь эффекта с квестом. VM stack ID, runtime FormID и offset — диагностические сведения, **не устойчивый ID награды**. Произвольный ObjectReference/Actor-скрипт с quest-property может не иметь такого self/родительского кадра: отсутствие контекста не доказывает отсутствие квестовой связи. XP, spell/ability rewards и прямое заполнение предметных алиасов не покрываются наблюдением AddItem.

При opt-in `TRUECOOP_QUEST_AUDIT=1` тестовая ветка выводит найденные источники на info-уровне, положительные локальные выдачи без источника — отдельно, а native Run — вместе с runner/executing thread ID. На master эта диагностика выключена. Обычный запуск не включает подробный аудит.

## Следующая локальная игровая проверка

Пользователь явно разрешил локальный gameplay-тест 18.11.2026, затем выбрал самостоятельное управление игрой/Vortex. В `Tools/TrueCoop/QuestProbe` подготовлены собственный диагностический quest/script и запускатель: одна выдача 17 золота через Papyrus, отдельный профиль/персонаж/серверный мир и отдельная папка сохранений. PEX скомпилирован Caprica 0.3.0 только из собственного скрипта и минимальных рукописных compile-only API declarations; vanilla/SKSE-скрипты не копировались. Плагин не переопределяет ни одной игровой записи и включается только в диагностический пакет. Процедура — `QUEST_AUDIT_INSTALL_RU.md`. **Игрового результата пока нет.** Дальнейшие отрицательные контроли покупки/loot и alias/ref ветви также требуют отдельного прохождения.

После этого: проверенная классификация/инициатор → отложенное решение сервера → фактическое применение и сохранённая клиентская квитанция → возврат VM. Только после проверки этих переходов можно включать доставку reward-планов в инвентари и объявлять отсутствие повторной выдачи после crash/load.

## Автоматическая проверка

112 Catch2 случаев / 3982 assertions, включая полное усечение нового кодека, распределение ключа/наград, неизменность receipt при повторе, конфликт, отказ чужого инициатора и непринятой стадии, атомарную ошибку индекса, restart, rollback, bounded paging, потерю одного получателя и миграцию schema 2 → 3. Это тесты протокольных данных/хранилища, а не Skyrim gameplay.

В трёх последовательных isolated paired-checkpoint прогонах прошёл save/rollback/restart/recovery. До исправления callback routing был один нестабильный отказ: TiltedConnect направлял process-wide disconnect в тот Client, чей `Update()` выполнялся в этот момент. Локальная overlay-реализация в `Code/transport` маршрутизирует скопированные статусы по connection handle и отдаёт каждый на собственном Update-потоке. Пин submodule сохранён. Это исправление сетевого транспорта, а не доказательство нативной загрузки Skyrim.
