# SKYRIM TRUE COOP

## Полное техническое задание для разработки с помощью Codex

### 1. Твоя роль

Ты — ведущий разработчик, системный архитектор и инженер по тестированию проекта **Skyrim True Coop**.

Твоя задача — помочь мне разработать полноценную кооперативную модификацию для **The Elder Scrolls V: Skyrim Special Edition в Steam**.

Я хочу создать мод, который превращает одиночную RPG в стабильную совместную игру, где несколько игроков существуют в одном мире, взаимодействуют с NPC, вместе проходят задания, принимают общие сюжетные решения и наблюдают одинаковые последствия своих действий.

**Главный принцип проекта — единый сюжет и единое прохождение для всех участников сервера.**

Все игроки должны иметь одинаковый прогресс квестов, одинаковое состояние сюжетных персонажей и общие последствия заданий. При этом у каждого остаётся собственный персонаж, инвентарь, навыки и возможность свободно исследовать мир.

Я не являюсь профессиональным C++-разработчиком, поэтому объясняй технические решения на русском языке, понятным языком.

**Главное правило:** ты не должен ограничиваться написанием планов и документации. После первоначального анализа архитектуры переходи к реальному написанию, сборке и тестированию кода.

При этом не пытайся реализовать весь проект за одну итерацию. Разбивай работу на небольшие, проверяемые изменения.

# 3. Главная концепция

Создать кооперативную модификацию для 2–4 игроков с возможностью расширения количества участников.

У каждого игрока:

- Собственный персонаж.
- Собственный инвентарь.
- Собственное развитие навыков.
- Собственная экипировка.
- Возможность самостоятельно исследовать мир.
- Возможность свободно перемещаться между локациями.
- Возможность участвовать в общих заданиях и событиях.
- Возможность принадлежать к разным фракциям в рамках общей системы гражданской войны.

Но **сюжет, прохождение заданий и состояние игрового мира должны быть общими для всех игроков**.

Если один игрок завершает квест, он должен считаться завершённым для всех участников соответствующего общего мира.

Если один игрок убивает важного сюжетного персонажа, этот персонаж должен считаться погибшим для всех.

Если один игрок открывает сюжетную дверь, она должна быть открыта для всех.

Если игроки выбирают определённый вариант развития сюжета, этот выбор должен действовать на весь сервер.

## Shared World State

Общее состояние игрового мира.

Включает:

- Состояние NPC.
- Погоду.
- Время суток.
- Состояние объектов.
- Изменения окружающего мира.
- Состояние дверей и контейнеров.
- Последствия сюжетных событий.
- Результаты гражданской войны.

## Shared Quest State

Единое состояние квестов.

Включает:

- Активные квесты.
- Текущие этапы.
- Выполненные задания.
- Сюжетные решения.
- Доступные диалоги.
- Состояние важных персонажей.
- Завершённые квесты.
- Последствия выполненных заданий.

**Никакого раздельного сюжетного прохождения быть не должно.**

Прогресс квестов должен принадлежать общему игровому миру, а не отдельному игроку.

При этом разрешается хранить личные характеристики персонажей и индивидуальные игровые данные, не влияющие на общий сюжет.

# 7. Единая система прохождения квестов

Это одна из главных особенностей проекта.

**Все игроки должны проходить один общий сюжет с единым прогрессом.**

Необходимо добиться того, чтобы квесты Skyrim корректно работали в кооперативе.

Например:

Игрок 1 получает задание поговорить с NPC.

Игрок 2 находится рядом или исследует другую локацию.

Когда игрок 1 выполняет необходимое действие, соответствующий этап задания должен завершиться у всех игроков.

Если игрок 2 выполняет следующую цель, общий квест должен продвинуться дальше для всех.

Участники могут выполнять разные действия, но прогресс задания всегда общий.

## 7.1. Shared Quest State

Разработай систему хранения единого состояния заданий.

Сервер должен хранить:

- Идентификатор квеста.
- Текущий этап.
- Выполненные цели.
- Активные цели.
- Принятые сюжетные решения.
- Состояние связанных NPC.
- Флаги важных событий.
- Данные о завершении квеста.

Изменения должны синхронизироваться между всеми подключёнными клиентами.

Не допускай ситуации, когда один игрок находится на пятом этапе задания, а другой на третьем.

При подключении нового игрока необходимо согласовать его игровое состояние с текущим общим состоянием сервера.

Если безопасно выполнить согласование невозможно, система должна предупредить игрока и не допускать повреждения сохранения.

## 7.2. Выполнение общих заданий

Необходимо обеспечить:

- Совместное принятие квестов.
- Единый журнал заданий.
- Синхронизацию текущих целей.
- Совместное выполнение заданий.
- Общее завершение квестов.
- Сохранение сюжетных решений.
- Синхронизацию связанных событий мира.

Если один игрок разговаривает с квестовым NPC, остальные должны получить соответствующее изменение квестового состояния.

Если один игрок побеждает квестового противника, общая цель должна обновиться у всех.

Если один игрок забирает сюжетный предмет, система должна учитывать его получение как общее достижение цели, не создавая дубликаты предмета.

## 7.3. Сюжетные решения

В игре существуют квесты, в которых необходимо выбирать варианты развития сюжета.

Предусмотри механизм принятия общего решения.

Возможные варианты:

**Leader Decision**

Решение принимает лидер группы.

**Group Vote**

Все участники голосуют, а сервер применяет один итоговый выбор по заранее определённым правилам.

На первоначальном этапе используй наиболее надёжный способ, совместимый с существующей архитектурой Skyrim Together Reborn.

После принятия решения оно становится общим для всех.

Нельзя допускать одновременного применения противоречащих сюжетных решений.

## 7.4. Диалоги

Исследуй возможность синхронизации важных диалогов.

Когда один игрок разговаривает с сюжетным NPC:

- Сервер определяет, что началось важное взаимодействие.
- Другие игроки не могут одновременно запустить конфликтующее сюжетное событие.
- Принятое решение применяется ко всему миру.
- Квестовый прогресс обновляется у всех участников.

Не обязательно заставлять всех игроков одновременно смотреть один диалог.

Главное — чтобы его последствия были общими.

## 7.5. Защита от рассинхронизации

Разработай механизмы предотвращения:

- Двойного завершения задания.
- Повторного запуска сюжетных сцен.
- Конфликтующих диалогов.
- Дублирования квестовых NPC.
- Разных этапов одного задания.
- Потери сюжетного прогресса.
- Повторного получения уникальных наград.

Сначала реализуй полноценную синхронизацию одного тестового квеста.

Затем постепенно расширяй поддержку оригинальных заданий Skyrim.

Не обещай идеальную синхронизацию всех квестов без индивидуального тестирования.

## 9.5. События вне сети

Не допускай ситуации, при которой игрок возвращается на сервер и обнаруживает полную потерю сюжетного прогресса из-за неконтролируемых событий, произошедших без него.

Предложи настраиваемые правила:

- Разрешены ли изменения территорий, когда участники офлайн.
- Как сервер сохраняет результаты.
- Какие события требуют присутствия игроков.
- Можно ли откатить ошибочное событие.

Учитывай, что общий мир может изменяться в отсутствие отдельного игрока, но эти изменения должны быть корректно сохранены и переданы ему при возвращении.

Начинай реализацию не с полной гражданской войны, а с одного тестового фракционного события.

# 10. Совместимость DLC

Это обязательная функциональная цель.

Я хочу, чтобы игроки с разными наборами официального контента могли находиться на одном сервере.

Например:

Игрок 1 использует Skyrim Special Edition с Anniversary Upgrade.

Игрок 2 использует только Skyrim Special Edition.

Они должны по возможности играть вместе без критических сбоев.

## 10.1. Content Detection

Разработай систему определения:

- Версии исполняемого файла Skyrim.
- Установленных официальных дополнений.
- Активных Creation Club / Creations.
- Активных ESP, ESM и ESL.
- Порядка загрузки.
- Версий необходимых компонентов кооператива.

Учитывай, что Dawnguard, Hearthfire и Dragonborn уже входят в Skyrim Special Edition.

Не путай версию исполняемого файла Skyrim с наличием платного Anniversary Upgrade.

## 10.2. Compatibility Manager

Создай механизм предварительной проверки совместимости.

Возможные результаты проверки:

**Compatible**

Совместная игра доступна.

**Limited Compatibility**

Подключение допускается, но определённые объекты или задания недоступны для совместного взаимодействия.

**Incompatible**

Подключение невозможно без изменения конфигурации.

Не допускай соединения с заведомо несовместимым контентом, если это может повредить сохранения.

## 10.3. Отсутствующие предметы и модели

Если один игрок использует предмет из дополнения, отсутствующего у другого:

1. Определи, существует ли безопасное совместимое представление предмета.
2. Если оно существует, используй предусмотренную визуальную замену.
3. Если замена невозможна, не передавай неподдерживаемый объект в игровой движок второго клиента.
4. Сохраняй корректное состояние предмета у владельца.
5. Не допускай потери или дублирования предметов.

Не применяй визуальные замены автоматически к объектам, если это нарушает работу квестов или игровой логики.

## 10.4. Разные DLC-квесты

Поскольку квестовый прогресс должен быть общим, необходимо определить правила доступности DLC-заданий.

Если у одного игрока установлен дополнительный контент, а у другого он отсутствует, нельзя запускать общий квест, который второй клиент не способен корректно обрабатывать.

Исследуй:

- Проверку наличия необходимого контента у участников.
- Предупреждение о недоступных заданиях.
- Возможность продолжать совместную игру в обычных локациях.
- Безопасное ограничение несовместимых квестов.
- Предотвращение рассинхронизации общего журнала заданий.

Общие DLC-квесты должны запускаться только тогда, когда у всех необходимых участников есть совместимые игровые ресурсы и права на их использование.

Не передавай защищённые платные ресурсы между игроками и не обходи проверку лицензий.

## 10.5. Совместное прохождение DLC

В перспективе хочу, чтобы игроки могли вместе проходить как можно больше официальных дополнений.

Но только при наличии у каждого необходимых файлов и прав на использование контента.

В первую очередь проверь возможность совместного прохождения Dawnguard, Dragonborn и других уже доступных обоим игрокам дополнений.

Anniversary Upgrade исследуй отдельно.

Не обещай полной совместимости до её фактического тестирования.

# 17. Обязательные тестовые сценарии

Для каждого этапа составляй проверяемые сценарии.

Минимальный набор:

**Тест A — подключение**

Два игрока входят в одно лобби и видят друг друга.

**Тест B — разные локации**

Игроки расходятся, исследуют разные локации и встречаются снова. Состояние общего мира остаётся согласованным.

**Тест C — один предмет**

Два игрока одновременно пытаются подобрать один предмет. Дублирование не происходит.

**Тест D — общий дом**

Первый игрок кладёт предмет в сундук, выходит из игры. Второй игрок подключается и обнаруживает сохранённый предмет.

**Тест E — разные DLC**

Игрок с Anniversary Upgrade подключается к игроку без платного Upgrade. Система правильно определяет различия и применяет предусмотренный безопасный режим либо объясняет несовместимость.

**Тест F — общий квест**

Два игрока начинают одно задание.

Первый игрок выполняет начальную цель.

Второй игрок получает обновление общего прогресса.

Затем второй игрок выполняет следующую цель.

Первый игрок также получает обновление.

В итоге задание завершается у обоих.

**Тест G — сюжетный NPC**

Первый игрок участвует в сюжетном событии, после которого важный NPC погибает.

Второй игрок после обновления состояния мира больше не должен видеть этого персонажа живым.

Изменение должно сохраняться после перезапуска сервера.

**Тест I — потеря соединения**

Игрок отключается во время важного события.

Оставшиеся участники завершают общий этап задания.

После повторного подключения отключившийся игрок получает актуальный общий прогресс.

**Тест J — перезапуск сервера**

После перезапуска сохраняются поддерживаемые изменения мира, домов и общего квестового состояния.

Для каждого теста указывай:

- Условия проведения.
- Последовательность действий.
- Ожидаемый результат.
- Фактический результат.
- Найденные ошибки.
- Способ исправления.

Не называй тест пройденным, если он не был фактически выполнен.

# 20. Формат отчёта после каждого задания

После выполнения каждой существенной задачи предоставляй отчёт на русском языке.

Структура отчёта:

**1. Что сделано**

Описание реализованных изменений.

**2. Какие файлы изменены**

Перечень файлов и назначение изменений.

**3. Что реально работает**

Только подтверждённая функциональность.

**4. Что проверено**

Запущенные тесты и результаты.

**5. Какие проблемы остались**

Ошибки, ограничения, риски.

**6. Что делать дальше**

Следующая небольшая задача из утверждённого плана.

**7. Что требуется от меня**

Только действия, которые ты не можешь выполнить самостоятельно: например, запуск Skyrim, проверка игры с другом или установка необходимых инструментов.

# 21. ТВОЁ ПЕРВОЕ ЗАДАНИЕ ПРЯМО СЕЙЧАС

Не начинай с гражданской войны, переработки квестов или переписывания сетевой системы.

Сначала:

1. Проанализируй реально доступный исходный код.
2. Определи текущие возможности Skyrim Together Reborn.
3. Определи ограничения и зависимости.
4. Проверь, что нужно для сборки в Windows.
5. Подготовь архитектуру будущих изменений.
6. Создай поэтапный план разработки с проверяемыми результатами.
7. Настрой или проверь процесс сборки.
8. Если необходимые инструменты доступны, попробуй собрать исходный проект без изменения игровой логики.
9. Покажи первый минимальный следующий шаг по реализации.

**После успешного выполнения этапа 1 переходи к улучшению стабильности синхронизации.**

Цель проекта — не просто написать много кода, а получить реально работающую модификацию Skyrim Special Edition с максимально полноценным кооперативом.

Главные требования:

- Один общий мир.
- Один общий сюжет.
- Единый квестовый прогресс.
- Одинаковые последствия сюжетных решений.
- Максимальная синхронизация персонажей, NPC и окружения.
- Удобные лобби и приглашения друзей.
- Общие дома и сохранения.
- Максимально возможная безопасная совместимость DLC.
- Единая динамическая гражданская война.

Всегда ориентируйся на конечный пользовательский результат.

Начинай работу с исследования репозитория и подготовки воспроизводимой сборки.
