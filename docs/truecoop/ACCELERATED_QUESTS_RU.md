# Ускоренный режим общего прохождения

Пользователь изменил требования: в первой версии квесты ведёт хост, предметные
эффекты получают оба игрока. Разделение предметов на «ключ» и «награду» для нового

## Реализованный путь

Режим включён для одинаковой сборки двух клиентов и сервера, Skyrim 1.7.104.0.
Оба игрока должны находиться в одной группе из двух человек. Хост берёт задания
и выбирает сюжетные ответы. Сервер принимает новые события общего журнала только
от лидера; от второго допускается точный повтор уже принятого события. Новое
независимое продвижение второго игрока отклоняется с требованием загрузить
соответствующее парное сохранение. Это контроль журнала, не перехват всего UI
диалогов или всех возможных путей запуска Papyrus.

Для стандартных AddItem/RemoveItem базовой формы в общих фрагментах этапов
(QF_ / Fragment_) подключён SharedQuestEffectService:

1. Хост запрашивает разрешение сервера. До разрешения оригинал не выполняется;
   native functor остаётся в штатной отложенной очереди, игровой поток не ждёт сеть.
2. Сервер проверяет текущий допуск, эпоху мира, лидера и постоянных участников,
   квест/эпоху запуска, формы и ограниченный размер эффекта. Резервируется до 64
   операций с тайм-аутом. Неизвестный ещё старт можно повторить после доставки
   события запуска; отказ никогда не трактуется как разрешение.
3. Оригинал выполняется хостом не более одного раза. Счётчик предметов читается
   непосредственно до/после него. В обычную репликацию инвентаря передаётся только
   фактическая разница; внутренние уведомления запрошенного количества подавлены.
4. Сервер сохраняет неизменяемую квитанцию Shared и оба индекса доставки одним
   действием. Положительный Count — выдача обоим, отрицательный — списание обоим.
   Нулевой фактический результат тоже получает квитанцию без изменения инвентаря,
   чтобы гостевой фрагмент мог подтвердить тот же no-op и продолжить работу.
   Гостевая копия вызова ждёт соответствующую квитанцию по отпечатку функции,
   инструкции и параметров, затем пропускает оригинал. До получения предмета
   VM гостя не продолжает проверки инвентаря. Если квитанция пришла раньше
   соответствующего гостевого вызова, применение ждёт этот вызов.
5. Хост сохраняет отметку уже выполненного оригинала, поэтому его входящая
   квитанция не выдаёт/списывает предмет второй раз. Гость применяет эффект с
   проверкой количества. Оба продвигают отдельные собственные сохранённые курсоры.
6. Повторные запросы курсора подтверждают применение. Только после обоих
   подтверждений VM хоста получает завершение операции. Это подтверждение живых
   globals/инвентаря, а не уже записанного ESS; следующий общий save сохраняет их
   вместе. Незавершённые операции блокируют общую контрольную точку и native save.

ID события содержит эпоху мира, серверный nonce допуска, cookie native-вызова
и отпечаток общего места вызова. Отпечаток сопоставляет гостевой вызов, а не
заменяет уникальный ID события: повторные вызовы цикла имеют отдельные cookie.
Сам VM stack ID и адрес инструкции не считаются постоянным ID. Сервер проверяет
nonce своего аутентифицированного соединения; два разных запуска процесса не
могут случайно повторить событие по одному лишь счётчику с единицы.

Запись quest-shared-run фиксирует **исполнителя будущих общих эффектов и пару**,
а не выдумывает исторического инициатора импортированного квеста. Исходная
quest-run/инициатор для прежнего классифицированного пути сохраняются. Импортированный
активный квест может получить только новую наблюдаемую выдачу, не повтор всех
прошлых наград. Смена лидера/состава в таком запуске не поддерживается.

Протокол: 0x5443000D; SQLite schema 5. Старые серверы отказываются открывать новую
схему. Записи квитанций, индексов и shared-run откатываются с парной точкой;
общая монотонная ревизия/эпоха и регистрация персонажей не переиспользуются.

## Границы первой реализации

- Поддерживаются обычные количества базовых форм, до миллиона за действие.
  Старый классифицированный формат сохранён; смешивать Shared и старые роли в
  одном плане нельзя. XP, способности, заклинания и свободные модовые скрипты
  не входят в этот путь.
- Наблюдатель определяет Quest/Alias/TopicInfo/Scene через проверенный стек,
  но новый производитель включает только QF_ / Fragment_ контекст Quest.
  Диалоговые/сценовые и произвольные helper-функции не имеют гарантированного
  гостевого повтора и остаются вне этого режима. Обычные покупки в меню, loot и расходование предметов вне этого
  контекста не копируются. **Стоимость, которую списывает сам квестовый скрипт,
  тоже является общим отрицательным эффектом**, без распознавания её смысла.
- Reference-valued операции, RemoveItem с другим контейнером назначения и
  неподдерживаемые формы проходят прежним native путём; для них общей выдачи
  этим брокером нет. Неизвестный источник также не угадывается.
- Этот производитель не восстанавливает индивидуальные алиасы, динамические
  зачарования, имена и произвольные свойства экземпляра. Обнаруженные варианты
  с extra data и несовпавший readback завершаются отказом/reload, а не сохранением
  частично подтверждённого результата. Поддержка всех квестовых ключей не заявлена.
- Для списания у гостя должно быть достаточное количество того же варианта.
  Недостача не заменяется списанием случайного зачарованного предмета или
  молчаливым подтверждением. Не продавайте/не расходуйте общие предметы до сдачи.
- Квестовые сцены, независимые ветки и восстановление VM после аварии требуют
  игровой проверки. Старое сохранение хоста без отметки исходного исполнения
  не получает Shared-эффект повторно: восстановление идёт через общую парную
  точку. Это не прозрачный recovery произвольного ESS после вылета.
  Вторая часть физики — полноценный дроп/подбор, движение
  предметов и точное согласование физики перед общей записью — остаётся отдельной
  незавершённой работой. Новый законченный ZIP на основании этого режима не заявлен.
