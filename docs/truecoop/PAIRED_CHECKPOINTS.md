# Парное сохранение и общая загрузка

Статус: исходники клиента/сервера реализованы, чистое хранилище и настоящий сетевой сервер проверены. **Два Skyrim-клиента ещё не проверены.** Это координация двух собственных ESS, а не перенос всей Papyrus VM/AI/Havok хоста во второй процесс.

Поддерживаемая движковая ветка этого модуля — **1.7.104.0**, ровно два разных персонажа в одной группе, один лидер. Новый ESP содержит четыре сохраняемых GLOB `TrueCoopCheckpointPart0..3` (0x4DFF–0x4E02). Нужен полный одинаковый пакет у обоих и новый сервер; протокол `0x54430009`, схема SQLite 2. Миграция схемы добавочная; старый сервер не открывает новую схему. Не заменять production-базу тестовой.

## Использование в тестовом профиле

1. После подключения и создания группы лидер пишет в сетевой чат `/coop-save`. QuickSave и ручное сохранение лидера тоже перехватываются, но первичную проверку проводить командой.
2. Оба клиента открывают штатный Journal Menu и проверяют настоящий флаг паузы. Дождаться сообщения «Общее сохранение №N готово». Сохранить номер N.
3. Изменить позиции обоих персонажей, контейнер/замок, пройти безопасную квестовую стадию. Лидер вводит `/coop-load N`.
4. До начала загрузки оба клиента сверяют размер и SHA-256 своих ESS и, при активном SKSE, co-save. Если файла нет или он изменён, мир не откатывается.
5. Сервер отсоединяет игровые сессии, очищает временные entity IDs, атомарно возвращает свой снимок и меняет эпоху. Клиенты загружают **каждый свой** файл, проверяют ID персонажа/сейва, переподключаются и ждут обоих. Прежний лидер сохраняется независимо от порядка входа.

F9 не перенаправлен на парный сейв: он может выбрать старый одиночный quicksave. Для общей загрузки использовать `/coop-load N`. Обычная загрузка чужого/непарного сейва по-прежнему отсоединяет от старой сетевой сессии.

Ограничение свежего ручного подключения: admission сейчас проверяет ID персонажа, токен сохранения и известную серверу ветку, **но не хеширует заново загруженный ESS**. Обычный одиночный сейв, сделанный после парного, может унаследовать тот же GLOB-токен. Токен сам по себе не доказывает, что текущий VM/инвентарь равен файлу manifest. Поэтому поддерживаемая проверяемая процедура rollback — именно `/coop-load`, где есть проверка обоих файлов и native load barrier. Загрузка произвольного локального сейва с ручным reconnect не получает гарантии точного восстановления; для неё ещё нужен отдельный протокол проверки происхождения нативного состояния.

Файлы имеют собственные уникальные имена `TrueCoop_<WorldId>_<checkpoint hex>_<CharacterId>.ess`; существующие слоты не перезаписываются. Не передавать ESS одного персонажа второму игроку. Копировать для резервного восстановления остановленную серверную папку и **оба** набора ESS/SKSE. Ненужные файлы после отменённого сохранения не считаются зафиксированной парой и не допускаются к откату.

## Что обеспечивает сервер

- ID файлов резервируются долговечно и не переиспользуются после отказа, рестарта или отката.
- Подтверждение одного игрока, чужая идентичность, неверный nonce и повторы не фиксируют пару.
- Снимок содержит серверные контейнеры/замки, журнал и остальные зарегистрированные записи текущей линии мира; полный упорядоченный manifest и каждая строка проверяются SHA-256.
- SQL rollback возвращает прежнее состояние при ошибке. Контракт модов и адаптеров не может измениться через загрузку. Общая ревизия никогда не уменьшается.
- Нормальная очистка уходящих игроков выполняется **до** отката; позднее закрытие сокетов не записывает состояние из будущего повторно.
- Старые пакеты отсекаются новой эпохой. Исключение — только проверенный `LoadNow`, адресованный текущей операции и переходящий вперёд.
- Маркер незавершённого возвращения игроков переживает перезапуск сервера. После успешного возвращения обоих он снимается долговечно; следующий рестарт не запускает повторный откат.
- База не хранит игровые ESS. Их подлинность здесь — проверка неизменности собственных файлов доверенного клиента, не защита от модифицированного клиента.

## Потоки и ограничения

Сеть не ждёт файловый worker. Worker получает копию пути и метаданных, читает/хеширует файл, проверяет стабильность и отдаёт значения через future. Engine API и запись GLOB выполняются на runner, CEF передаёт только копию намерения. Во время барьера обычная игровая репликация/очередь приостанавливаются, транспорт продолжает работать. При позднем исходящем gameplay-событии сохранение отменяется. Отмена, несоответствие файлов и timeout размораживают клиент; timeout после загрузки закрывает также незавершённую игровую сессию.

**Нативная сериализация Skyrim сама синхронно захватывает VM/мир под движковыми save-locks.** Перенести её на произвольный worker безопасно нельзя. Отсутствие дополнительного ожидания сетевого ACK на кадре не означает отсутствие обычной паузы записи ESS. p95/p99, native Journal pause, появление уникальных имён в меню и фактическое восстановление обоих персонажей требуют игрового теста.

Парный откат восстанавливает то, что каждый клиент записал в своём ESS. Он пока не исправляет исходно разные NPC, ragdoll, мебель или несинхронизированный динамический дроп. Серверный backend WorldItem ещё не соединён с полной игровой репликацией. Нельзя объявлять точное совпадение всего мира или нулевые микрофризы.

## Квестовые предметы и награды

Удалена конкретная ошибочная выдача: `TESObjectREFR::AddOrRemoveItem` больше не копирует квестовый предмет из реплицируемого инвентаря удалённого персонажа в локального игрока.

Для нового квестового запуска сервер теперь атомарно с первым принятым событием пишет `quest-run/<quest>/<epoch>`: инициатор и две постоянные идентичности участников. Повтор события/другая сторона не меняют владельца; перезапуск квеста создаёт новую запись; откат возвращает прежние записи. Импортированный журнал не получает выдуманного инициатора от отправителя следующей стадии.

Это **не завершённая выдача** «ключевой предмет инициатору / награда обоим». Подавление отложенного Papyrus AddItem, алиасы, предметы из dialogue/scene fragments и квитанции фактически выданной награды ещё не подключены. Ghidra показала, что AddItem выполняется отдельным delay-functor со stackID, а не внутри синхронного SetStage: простой TLS вокруг SetStage ненадёжен. Во время продолжения MCP потерял открытую программу; неподтверждённый VM/alias hook не добавлен.

## Автоматические проверки

- 104 Catch2 случая / 3412 assertions: кодеки, отказ усечённых пакетов, допуск перехода эпохи, атомарность/контроль целостности снимка, неизменный контракт, долговечность инициатора, откат квестового запуска.
- Шесть проверок структуры ESP и неизменности прежних записей.
- Headless реальный сервер: сохранение/rollback, повтор/wrong nonce/чужая identity, новый epoch, отказ старого сейва, обратный вход участников и прежний лидер.
- Отдельно: рестарт между rollback и rejoin, отказ постороннего, восстановление зависшего rendezvous; ещё один рестарт после завершения без повторной заморозки.

Повторяемый сценарий: `Tools/TrueCoop/Test-PairedCheckpoints.ps1`. Он создаёт отдельный мир с синтетическими данными в workspace/work, запускает скрытые тестовые серверы, проверяет их PID+путь перед остановкой и не запускает Skyrim/Vortex. Результат протокола не заменяет игровой тест.
